Factory and core services

Object vs component

uvm_object is data. No parent, no phases, created and discarded freely — sequence items, sequences, register model classes. uvm_component is structure. It has a parent, a full hierarchical name, and it runs phases. Built once in build_phase, alive for the whole simulation.

That split is why the utils macros differ, and why a sequence is created with type_id::create(name) while a component needs type_id::create(name, this) — the second argument is the parent, which only components have.

What run_test() creates, in order

  1. Static initialization. Every `uvm_*_utils macro registers a uvm_object_wrapper singleton with the factory. Nothing is instantiated yet — the factory only learns what types exist.
  2. uvm_coreservice_t on first access, which creates the factory, the report server, and uvm_root.
  3. uvm_root is itself a component — the only one with no parent. Its instance name is the empty string, which is why it never appears in a path. The global handle is uvm_top.
  4. run_test("my_test") forwards to uvm_root::get().run_test(...). A +UVM_TESTNAME= plusarg overrides the string argument.
  5. The test component — the first thing your code owns. Created as create_component_by_name(test_name, "", "uvm_test_top", null). The instance name is always uvm_test_top regardless of your class name, which is why override paths read uvm_test_top.env.agent.driver.
  6. build_phase runs top-down: test creates env, env creates agents, agents create driver / monitor / sequencer.
  7. connect_phase and end_of_elaboration bottom-up, start_of_simulation top-down. All zero-time.
  8. run_phase — the first phase that consumes time, and where sequence items start being created and discarded continuously.
